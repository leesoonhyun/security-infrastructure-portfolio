## 실습 범위

2단원 후반에는 취약 C 코드와 Linux 시스템 과제를 통해 입력값·메모리·파일·권한 설정이 보안에 미치는 영향을 확인했습니다.

### 취약 코드 예제

| 파일 | 주제 | 관찰한 문제 | 방어 관점 |
|---|---|---|---|
| `bof1`, `bof2` | 고정 크기 버퍼와 `strcpy` | 길이 제한 없는 복사로 인접 메모리 손상 가능 | 길이 검증, 안전한 API, 컴파일러 보호기법 |
| `bof3` | 인증 상태 변수 | 버퍼와 인접한 인증 변수가 입력에 의해 바뀔 수 있음 | 인증 상태 분리, 안전한 입력, 방어적 컴파일 |
| `bof4` | 명령 버퍼 | 사용자 입력이 실행 명령에 영향을 줄 수 있음 | 외부 명령 제거, 허용목록, 입력·인자 분리 |
| `format1` | `printf(user_input)` | 포맷스트링에 따른 메모리 노출 가능 | `printf("%s", user_input)` 사용 |
| `format2` | `%n` 계열 영향 | 포맷스트링이 메모리 값을 바꿀 수 있음 | 포맷 고정, 경고 옵션, 정적 분석 |

### 시스템·운영 과제

- 사용자 계정과 로그인 셸 목록 점검
- 파일·백업·자원 사용량 확인
- 네트워크·웹 서비스 상태 점검 스크립트
- CPU·메모리 임계치 모니터링
- 취약점 점검 결과와 로그·리포트 생성

## BOF 학습 흐름

```text
정상 길이 입력
  -> 버퍼·인접 변수 상태 확인
긴 입력
  -> 종료 상태·오류·변수 변화 관찰
소스 비교
  -> 길이 검증과 안전한 함수로 수정
재실행
  -> 비정상 입력이 차단되는지 확인
```

## Format String 학습 흐름

취약 호출과 안전한 호출을 비교했습니다.

```c
/* vulnerable */
printf(user_input);

/* safer */
printf("%s", user_input);
```

핵심은 특정 페이로드를 외우는 것이 아니라, **사용자 입력이 명령·포맷·메모리 구조로 해석되지 않도록 데이터와 제어문을 분리하는 것**이었습니다.

## 컴파일·운영 관점의 방어

- `-Wall -Wextra`로 경고 확인
- Stack Canary, NX, PIE, ASLR 등 보호기법의 역할 이해
- 입력 길이와 종료문자 처리
- 외부 명령 사용 시 shell을 거치지 않고 인자 배열 사용
- SUID·sudo·capability의 최소 권한과 정기 점검
